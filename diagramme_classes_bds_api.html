Notes de lecture

  • User est abstraite : seules ses sous-classes Member et Administrator sont instanciées, via un héritage par table jointe (même id partagé, colonnes propres à chaque table).
  • Player est distinct d'un compte User : un administrateur crée un Player avant même que la personne ait un compte ; user_id (nullable, unique) n'est renseigné qu'une fois le RegistrationCode consommé.
  • FixtureResult est une table séparée de Fixture (composition) — un match programmé mais pas encore joué n'a tout simplement pas de ligne de résultat, plutôt que des colonnes home_score/away_score nullable et donc ambiguës.
  • ActivityPaymentDue pointe vers soit un ActivityInstallment, soit un ActivityDeposit, jamais les deux, jamais aucun des deux — une CheckConstraint peut l'imposer en base si l'équipe veut aller plus loin que le stub actuel.
  • MatchPrediction est volontairement indépendante de Prediction/MLModel (hors périmètre) : elle est notée contre le vrai résultat d'un match, jamais contre la sortie d'un modèle.
  • Les cartes grisées en fin de page (MLModel, Prediction, EmailNotification) sont des stubs qui documentent explicitement pourquoi elles ne sont pas construites — rien n'est silencieusement vide dans ce squelette.
